# 06 · 表快照、演进与查询层职责

## 目标与前置

完成 02、04–05。理解文件为何还需要表元数据、多个分区规范如何共存，以及查询引擎在哪里裁剪。本章是阅读与设计拓展，没有执行 Iceberg 部署。

## 一个目录不等于已提交的表

假设写者要生成 A、B 两个文件，却在 B 出现前崩溃。列举目录的读者可能看到不完整集合。表格式增加元数据，描述某次提交所包含的数据文件与删除文件。Iceberg 的表元数据追踪快照与引用，Manifest 描述文件成员及统计；Catalog 参与定位和提交表元数据。具体原子提交机制取决于 Catalog 与存储集成。

快照选择文件集合，不代表每次提交都复制全部数据。旧快照可能仍引用旧文件；过期快照和删除无引用文件属于维护操作，有保留期与并发条件。只凭对象年龄删除“看起来旧”的文件，可能破坏仍需要它的读者。

## Schema 与分区演进

字段改名或调整位置时，身份标识很重要；稳定的字段 ID 可以避免把同一位置的新列误认成旧列。分区演进允许旧文件保留旧规范，新文件采用新规范，二者共存。规划器按各自规范解释谓词。修改规范不代表所有旧文件都已物理重写。

## 查询引擎仍然有工作

分析引擎可以逐层裁剪：快照成员、分区/文件统计、Parquet Row Group 统计，可能还有页索引，最后执行精确行条件。各层权威与粒度不同。选列减少数据请求，与选行是独立问题。表格式不执行 SQL；查询引擎也不会让任意目录列举自动变成事务。

HDFS 可以是存储选项，对象存储也可以。本版不会创建 AWS 资源，更不会用本地兼容服务冒充验证真实 AWS 语义。CockroachDB 的事务路线与文件/表路线仍然分开。

## 数据与设计任务

在纸上写一份合成清单：快照 S1 引用按月分区的 A/B，S2 引用 A/B/C，其中 C 按日分区。针对某一天的条件，标出分区元数据可排除什么、还需什么文件统计。再添加 S3，用 D 替换 B；如果仍保留 S1，判断能否删除 B。

## 预期结果与解释

S2 可以混合规范，无需重写 A/B。较粗的月分区可能把整月保留为候选，按日分区的文件则可更精细地判断。保留的 S1 仍需要 B。这些是推理答案，不是引擎扫描实测。若继续做第四个可执行项目，应固定 Iceberg、Catalog 与引擎版本，记录提交冲突，检查快照元数据并验证新旧规范；证据应与本版已经执行的三个 Profile 分开。

## 自测

**新快照必须复制每个 Parquet 文件吗？** 不用。**分区演进自动重写历史吗？** 不会。**本地 S3 兼容 API 能证明 AWS 真实故障行为吗？** 不能。**表级裁剪能代替精确行过滤吗？** 通常不能，候选文件仍可能包含不匹配行。
